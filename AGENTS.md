# safe-mjml - Native Go MJML Compiler

## Project Overview
A native Go implementation of the MJML email framework for compiling MJML markup to responsive HTML. 100% feature-complete with all 26 MJML components implemented and thoroughly tested against reference implementation.

## Repository
This project is developed in **[Notifuse/safe-mjml](https://github.com/Notifuse/safe-mjml)**. It started as a fork of [preslavrachev/gomjml](https://github.com/preslavrachev/gomjml).
- Open pull requests against `Notifuse/safe-mjml` (`main`).
- The Go module path is `github.com/Notifuse/safe-mjml`; the public package is `mjml`, and the CLI is `safe-mjml`.

## Architecture Checks
Before an architecture review or a release, run the checks in [docs/architecture-checklist.md](docs/architecture-checklist.md): consumer costs (binary size under reflection, API surface, globals, CPU-dependent output), code structure, strictness of the test oracle, runtime performance, CI and docs. Measure each item rather than reasoning about it.

## Reference
MJML 4.18 is the reference. Each case of `mjml/testdata` has the HTML MJML 4.18 renders, generated by `tools/mjml-reference` (`node regenerate.mjs <case>`), and the integration tests compare safe-mjml's output with it; `mjml/testdata/AGENTS.md` describes the comparison and the documented deviations.

## Key Architecture
- **CLI Application**: `cmd/safe-mjml/` with compile and test commands
- **Core Library**: `mjml/` package (importable) with component system
- **Parser**: `internal/parser/` package for XML/AST processing
- **Components**: Individual MJML component implementations in `internal/components/`
- **Forks**: `internal/juicer` (inline `mj-style`) and `internal/cascadia` (selectors) are forks of go-juicer and cascadia; [docs/forks.md](docs/forks.md) gives their starting points, what safe-mjml changed, and how to port upstream commits

## Build & Test Commands
```bash
# Build CLI (for debugging, always use debug build)
go build -tags debug -o bin/safe-mjml ./cmd/safe-mjml

# Build production version (no debug output)
go build -o bin/safe-mjml ./cmd/safe-mjml

# Run integration tests (against reference implementation)
./bin/safe-mjml test

# Run tests with verbose output
./bin/safe-mjml test -v

# Run tests matching pattern
./bin/safe-mjml test -pattern "basic"

# Run integration tests with debug build for detailed output
go test -tags debug -v ./mjml -run TestMJMLAgainstExpected

# Byte-for-byte snapshots of the current output (mjml/testdata/snapshots/):
# must stay unchanged during a refactoring; rewrite them only when a change of
# output is intended, and review their diff
go test ./mjml -run TestRenderSnapshots
go test ./mjml -run TestRenderSnapshots -update

# Run benchmarks
./bench.sh

# Test case comparison with htmlcompare utility
# First build the utility:
go build -o bin/htmlcompare ./cmd/htmlcompare

# Option 1: Run from mjml/testdata/ (auto-detects location):
cd mjml/testdata
../../bin/htmlcompare basic                    # Compare basic.mjml vs basic.html
../../bin/htmlcompare basic --verbose          # Show more diff context

# Option 2: Run from project root (specify testdata directory):
./bin/htmlcompare basic --testdata-dir mjml/testdata         # Compare from root
./bin/htmlcompare mj-button-align --testdata-dir mjml/testdata
./bin/htmlcompare basic -v --testdata-dir mjml/testdata      # Verbose output

# The utility auto-detects project root, builds debug safe-mjml, and performs semantic HTML comparison

# Compile MJML to HTML
./bin/safe-mjml compile input.mjml -o output.html

# Compile with debug attributes for troubleshooting
./bin/safe-mjml compile input.mjml -o output.html --debug

# Debug compile with verbose logging: use the debug build (-tags debug, above)
./bin/safe-mjml compile input.mjml -o output.html
```

## Development Guidelines

### Component Interface & Architecture
- **Component Interface**: All components implement `Render(w io.StringWriter) error` and `GetTagName() string`
- **Base Component**: Extend `*BaseComponent` which provides common functionality and attribute handling
- **Testing**: Integration tests validate against reference implementation. Never rewrite a test so that it passes: when a fix changes what an existing test expects, its input stays and becomes a case compared with MJML 4.18 (see "When a fix changes what an existing test expects" in mjml/testdata/AGENTS.md)
- **Performance Focus**: Recent commits show memory optimizations and performance improvements
- **Email Compatibility**: Generates MSO-compatible HTML for Outlook/Gmail/Apple Mail

### Component Implementation Standards

#### HTML Generation
- **Use HTMLTag Builder**: Use `html.NewHTMLTag()` for generating HTML elements instead of string concatenation
- **StringWriter Pattern**: All internal rendering methods must use `io.StringWriter` interface for performance
- **Constants Usage**: Use constants from `internal/constants` package instead of hardcoded strings:
  - CSS properties: `constants.CSSFontSize`, `constants.CSSPadding`, etc.
  - HTML attributes: `constants.AttrClass`, `constants.AttrCellSpacing`, etc.
  - MJML attributes: `constants.MJMLFontFamily`, `constants.MJMLPadding`, etc.
  - Common values: `constants.VAlignMiddle`, `constants.AlignCenter`, etc.
  - Language/Direction: `constants.LangUndetermined`, `constants.DirAuto`, etc.
  - **🚨 Code Review Check**: Always look for magic strings that should be constants!

#### Code Structure
- **Fonts**: the head imports the fonts whose names appear in a font-family of the rendered body or of the inline mj-style rules, as mjml-core's buildFontsTags does (`fonts.ToImport`, which scans the output once); a component needs nothing more to have its fonts imported.
- **Attribute Handling**:
  - Read every attribute with `c.resolveAttribute(c, name)`: it merges, as mjml-core does, the element, the tags inside the mj-class of its nearest classed ancestor (classesDefault), its own mj-class, mj-attributes for its tag, what the parent passes down, mj-all, then the component default. An attribute set to the empty string stays empty.
  - Don't write wrapper `getAttribute` methods. A parent that passes attributes down to its children (as MJML's `renderChildren` does) sets `ChildContext.PassedAttributes` in its `childContext`.
  - Read the element alone (`c.Node.GetAttribute(name)`) only where MJML reads `rawAttrs`, such as the explicit font-family of accordion titles and texts.
- **Individual Padding**: Support individual padding properties (`padding-top`, `padding-bottom`, etc.) alongside general `padding`
- **MSO Compatibility**: Use MSO conditional comments for Outlook-specific elements: `<!--[if !mso | IE]><!--> ... <!--<![endif]-->`
- **CSS Class Support**: the `css-class` of a content component goes on the cell its column or hero writes around it (`renderInCell`); containers write it on their main element with `c.buildClassAttribute()`, as MJML does

#### Example Pattern
A content component writes its own markup only: the mj-column or mj-hero it
stands in writes the row and cell around it (`renderInCell`, as MJML's
renderColumn), from its align, css-class, container-background-color and
padding.

```go
func (c *MyComponent) Render(w io.StringWriter) error {
    // Get attributes using constants
    fontFamily := c.resolveAttribute(c, constants.MJMLFontFamily)

    // Use HTMLTag builder
    div := html.NewHTMLTag("div").
        AddStyle(constants.CSSFontFamily, fontFamily)

    if err := div.RenderOpen(w); err != nil {
        return err
    }

    // Render content...

    return div.RenderClose(w)
}

func (c *MyComponent) GetTagName() string {
    return "mj-my-component"
}
```

## AST Caching (Performance Feature)

### Overview
The AST cache improves performance by storing parsed MJML templates in memory. This is an **opt-in feature** disabled by default.

### Usage
```go
// A cache lives as long as the application; Close stops its cleanup goroutine
cache := mjml.NewCache(10 * time.Minute) // TTL; 0 means 5 minutes
defer cache.Close()

html, err := mjml.Render(template, mjml.WithCache(cache))
```

The CLI compiles one file per run and has no cache option.

### Configuration
- **Default TTL**: 5 minutes, counted from the parse (a hit does not extend it)
- **Cleanup interval**: TTL/2
- **Thread-safe**: All operations safe for concurrent usage
- **Memory growth**: No size limits - monitor memory usage in production

### When to Use Caching
- High-volume applications with template reuse
- Web servers rendering the same templates repeatedly  
- Batch processing with repeated templates
- Applications where parsing time > rendering time

### When NOT to Use Caching
- Single-use template rendering
- Memory-constrained environments
- Applications with constantly changing templates
- Short-lived processes where cache warmup overhead > benefits

### Memory Considerations
- **Cache growth**: Unbounded between cleanup cycles, and unbounded in size
- **Memory usage**: about 7 times the template for the parsed tree, plus the template itself, kept as the key (32 templates of 1 MB, mostly a comment, kept 33.8 MB); there is no size limit, so the TTL and Close are what bound it, on the caller's side
- **Cleanup strategy**: Background goroutine removes expired entries
- **Production monitoring**: Watch memory usage for cache size estimation

### Technical Implementation
- **Package**: `internal/astcache`; `mjml.Cache` wraps it, and no state is global
- **Concurrency**: Uses singleflight pattern to prevent duplicate parsing under load
- **Storage**: `sync.Map` keyed by the template itself, optimized for high read/low write workloads
- **Expiration**: Fixed TTL with background cleanup (no LRU complexity)
